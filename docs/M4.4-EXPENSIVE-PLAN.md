## 0. 執行協定（最高優先，違反即為失敗）

### 0.1 不提問
全程不得向使用者提問，包含確認、選擇、澄清。

### 0.2 工作循環
    階段實作 → 執行 ./verify.sh → 全綠？
                                  ├─ 是 → 下一階段
                                  └─ 否 → 自動修正 → 重跑

### 0.3 錯誤指紋斷路器【條款 1】
每次修正前，取失敗訊息的前三行做正規化後雜湊，得到一枚「錯誤指紋」，記錄下來。
若同一枚指紋第二次出現，**立刻停止該項目**，寫入 BLOCKERS.md
（含指紋、完整錯誤、已嘗試的修法、你判斷的根因），然後繼續處理其他項目。
輪數上限作為第二道防線，設為 3。
**不得為了讓指紋不同而改寫錯誤訊息或包裝例外。**

### 0.4 分層驗收【條款 2】
verify.sh 分三層，依序執行，前一層失敗就不進入後一層：

- **L1（秒級）**：靜態檢查、匯入檢查、grep 類的結構與架構檢查
- **L2（十秒級）**：單元測試與編譯（`:core:test`、`:app:compileDebugKotlin`、`node --test`），不含覆蓋率統計
- **L3（分鐘級）**：`assembleDebug`（會編譯所有資源檔，XML 寫錯在這裡才會發現）、Lint、突變測試、報告、完整回歸

**各階段的驗收只跑 L1 與 L2（`./verify.sh`）。L3（`./verify.sh --full`）只在最後一個階段跑一次。**
不得在 verify.sh 中吞掉任何一層的失敗回傳碼。
因為資源檔的錯誤只有 `assembleDebug` 看得出來，T2 與 T3 完成時各允許額外跑一次 `./gradlew :app:assembleDebug`（這是本批次對條款 2 的唯一例外，只跑這一個指令，不跑整套 L3）。

### 0.5 成本記錄【條款 6】
每階段結束時在 PROGRESS.md 記錄：該階段的修正輪數、出現過的錯誤指紋清單、每個驗收項各失敗過幾次。

### 4.1 `core/.../drink/SettingsError.kt`（新增，純函式，不 import android，不連網，不讀時間）

```kotlin
// 常數定義
const val SETTINGS_ERROR_PREFIX = "設定值不正確："   // Worker 回報欄位錯誤的固定開頭（與 backend/core/drink.js 的 SETTINGS_ERROR_PREFIX 相同）

// 設定頁的五個欄位；label 與 backend/core/drink.js 的 SETTING_RULES 的 label 逐字相同（A75）
enum class SettingsField(val label: String) {
    NAME("訂閱名稱"),
    FEE("月費"),
    RESIST("忍住一杯的入帳金額"),
    QUOTA("每月額度"),
    ASK("每天詢問時間"),
}

// 從 Worker 回的錯誤訊息找出是哪個欄位。
// 規則：訊息必須以 SETTINGS_ERROR_PREFIX 開頭，且去掉開頭、再去掉前後空白後，恰好等於某個欄位的 label，才回傳該欄位；
// 其餘（null、沒有開頭、開頭之後不是五個 label 之一、只有開頭沒有名稱、「啟用戒飲記錄」、「已儲存」、連不上的提示）一律回 null。
// 不做模糊比對、不做包含比對。
fun settingsFieldOf(message: String?): SettingsField?
```

### 4.3 標紅與清除（A71～A73）

在 `DrinkSettingsActivity` 內新增（私有、追加）：

```kotlin
// 目前被標紅的欄位（畫面狀態，不存本機；A76）
private var markedField: SettingsField? = null

// 把某個欄位標紅（先清掉舊的）；null 表示不標任何欄位
private fun markField(field: SettingsField?)
// 清掉所有紅框
private fun clearMark()
```

- 儲存流程中，**兩個步驟**的結果訊息都做同一件事：把結果顯示到狀態列（現有行為），再 `markField(settingsFieldOf(message))`。成功（`SETTINGS_SAVED_MESSAGE`）時 `settingsFieldOf` 回 null，所以紅框會被清掉（M44-S09）。
- 每次按「儲存」開始時 `clearMark()`；`loadSettings()` 開始時也 `clearMark()`。
- 標紅後，使用者開始修改**該欄**的內容（`TextWatcher.afterTextChanged`，或選單改選）時，清掉那一欄的紅框，其他欄不受影響（手機實測 D05；不進規格測試，見 §6.3）。
- 欄位與 `SettingsField` 的對應只寫在一個小函式 `viewOf(field)`（`when` 表達式）；**不得**在 Activity 內以字串比對訊息（A71）。
- 開關那一步的錯誤（「設定值不正確：啟用戒飲記錄」）`settingsFieldOf` 回 null → 不標紅任何文字欄位，已存的五個欄位不回滾（M44-S08；現有行為）。
- 標紅只改該欄輸入框的背景（`bg_settings_field_invalid`），不改文字、不顯示任何逐欄文字（A72）。
- **逐項保持 M4.3 的檢查**：`saveSettings` 內仍只含 `WorkerApi.put(SETTINGS_PATH`、不含 `ENABLED_PATH`、不含 `"enabled"`，且 `return@put` 仍在 `saveEnabled()` 之前；`saveEnabled` 內仍有 `WorkerApi.put(ENABLED_PATH` 與 `"enabled"`；整個檔案中 `"enabled"` 只出現在 `ENABLED_PATH` 附近 8 行內。若新增的標紅程式需要在這些函式內寫字串，不得使用 `"enabled"` 這個字面值。

## 8. 絕對禁止事項

- 不得向使用者提問。
- 不得連線真實外部服務、不得呼叫真實 API（驗收全程只用 stub）。唯一例外：突變測試工具無法執行時，可唯讀瀏覽 GitHub 搜尋替代品（見 §7），結果不影響任何驗收判定。
- 不得建立含真實憑證的檔案；不得在 log、錯誤訊息、回應中寫出存取密鑰或伺服器回應內容。
- 不得設遠端、不得 push、不得部署（`wrangler deploy`、`wrangler secret`、`d1 execute --remote` 一律不執行）。
- 不得刪除或覆蓋既有檔案內容；`colors.xml` 只能追加；既有的 `res/drawable/*.xml`、`themes.xml`、`strings.xml` 不動。
- 不得修改 §1「不動」列的任何檔案；特別是主畫面（`activity_main.xml`、`MainActivity.kt`）、`backend/` 全部、`Drink.kt`、`OverlayService.kt`、所有圖片檔。
- 不得改變 `DrinkSettingsActivity` 的儲存流程、送出內容、欄位數量、欄位名稱常數、兩步驟順序。
- 不得把 `enabled` 加進設定的 body。
- 不得新增 `@JavascriptInterface`；不得新增本機儲存。
- 不得在 `DrinkSettingsActivity` 內用字串比對 Worker 的錯誤訊息（A71）。
- 不得新增逐欄的錯誤文字元件（A72）。
- 不得改寫使用者確認過的任何句子（§4.2 的畫面文字、§4.6 的預期結果）。
- T0b 之後不得修改兩個 spec 目錄的任何檔案。
- 不得自製突變量測工具；不得 clone、下載、安裝或執行搜尋到的替代品。
- 不得安裝與本計畫無關的套件（含任何 UI 套件、動畫套件、圖示套件）。
- 不得執行 `docs/M4.4-CHEAP-PLAN.md` 的內容。
