# 平行分派代理人的流程（M1.6 首次實行，2026-10-04）

> 本專案第一次把一個里程碑拆成多條線，同時派多個代理人在各自的 git worktree 開工，再由規劃者整合。
> M1.6（懸浮窗表情演出）從規劃到手機實測通過都在同一天完成。這份文件記錄做法、實際數字與踩到的坑，M2 之後照著用。
> 2026-10-05 M2（戒飲記錄）第二次照做，數字與新踩到的坑補在 §5.1、§6、§7。

## 1. 什麼時候值得平行

- **值得**：工作能切成幾塊「只靠事先定好的接口互相溝通」的部分，例如 Worker、Kotlin、角色頁。M2（Worker 規則＋LLM 解析＋App 按鈕）比 M1.6 更適合。
- **不值得**：幾秒鐘就做完的事（例如放表情圖），或每塊都要改同一個檔案的工作。
- **代價**：每個代理人都從零開始讀專案，token 用量比一個人做多；前置與整合省不掉。M1.6 的實作階段從約一小時縮到約 7 分鐘（最慢的 B 線），但前置花的時間比實作還多。

## 2. 前置動作（規劃者在派工前完成）

| # | 動作 | M1.6 的做法 |
|---|---|---|
| 1 | commit 所有未提交的改動 | worktree 只帶得走已 commit 的內容 |
| 2 | 準備 worktree 用的本機檔 | `tools/prepare-worktree.sh`：複製不進 git 的 `local.properties`、`firebase.properties`、`worker.properties`、角色圖，並 `npm install --no-package-lock` |
| 3 | 跑便宜批次 | 契約檔、文件、實測清單先寫好（docs/M1.6-CHEAP-PLAN.md） |
| 4 | 定接口，寫進貴批次計畫書 §4 | 推播格式 `{id, text, script?}`、JS 介面 `window.pet.say(script)`、表情鍵與檔名（`emotion-map.js`） |
| 5 | 定檔案所有權，寫進計畫書 §1 | 每個檔案只歸一條線；共用文件（PROGRESS、DECISIONS、報告）只由規劃者寫；各線只寫自己的 `lanes/M1.6-<線>.md` |
| 6 | 規格範例表給使用者逐列確認 | 15 列全部打勾；確認後才轉成測試 |
| 7 | 凍結規格測試 | 凍結前先寫草稿實作確認測試「能被滿足」，再刪掉草稿 |
| 8 | `verify.sh` 加 `--lane` | L1 三條線都全跑；L2 只跑該線負責的部分；`--full` 只在整合時跑 |
| 9 | 確認起跑狀態 | 在 master 分別跑三條線的檢查，每條線都只卡在自己還沒實作的規格列 |
| 10 | 開 worktree、派工 | `git worktree add -b m16-lane-<x> ../pet-maid-m16-<x>`＋準備腳本；三個代理人在背景同時執行 |

## 3. 派工給代理人的內容

每個代理人的指示只有：工作目錄（worktree 絕對路徑）、它是哪一條線、讀計畫書的哪幾節、只能跑 `./verify.sh --lane <線>`、只能在自己的分支 commit、完成後照 §9 的格式回報。其餘全部寫在計畫書裡，不在派工訊息裡重複。

## 4. 整合（規劃者）

1. 依計畫書的順序合併（M1.6：D → C → B），使用 `--no-ff`，保留各線的 commit
2. 處理各線回報的「需要整合處理」
3. `./verify.sh --full` 一次
4. 依各線紀錄檔的「高風險函式」段落寫 RISK-REVIEW；依「進度」段落寫 PROGRESS 與 ACCEPTANCE 的成本表
5. 移除 worktree 與分支

## 6. 踩到的坑與對策

| 坑 | 發生在 | 對策 |
|---|---|---|
| 規劃者產生的 `verify.sh` 裡，sed 的 `\1` 變成 0x01 位元組，V28 永遠失敗 | B 線 | 含反斜線的內容一律用檔案工具寫，不用 shell heredoc；寫完用 `LC_ALL=C grep` 掃控制字元。**驗收腳本本身也要在起跑前實際跑過會觸發的路徑** |
| 代理人用 heredoc 寫 Kotlin，`\n` 變成真的換行 | C 線 | 同上 |
| `npm install` 在 worktree 留下未追蹤的 `package-lock.json`，三條線都回報 | 全部 | 準備腳本加 `--no-package-lock` |
| 規格寫的是「照抄 accompany_bot」，但凍結的規格和 accompany_bot 差一個字的時間 | B 線 | 代理人以凍結規格為準並記錄；規劃者在整合時向使用者說明 |
| 代理人碰到別線的檔案或契約檔有問題 | B 線 | 規則是「不改，寫進紀錄檔的『需要整合處理』」，這次運作正常：B 線沒有自己改 `verify.sh`，而是附上佐證回報 |
| M2 修訂了 A12（App 可以連 Worker），但 M0 凍結的 S15 仍然禁止所有 `HttpURLConnection`。代理人改用 `HttpsURLConnection` 避開字面檢查 | M2 C 線 | 代理人沒有改凍結測試，而是回報成規格爭議，規則有效。對策是修訂約束時，同時搜尋舊的凍結規格；`verify.sh` 的禁用字要包含同類的寫法（V18 已加上 `HttpsURLConnection`、`openConnection`、`java.net.`） |
| Stryker 指令寫成 `tests/spec/m2/*.test.js`，把會讀角色頁的 `overlay-drink.test.js` 也帶進沙盒，初始執行失敗 | M2 整合 | 指令改成逐一列出測試檔。`--lane D` 不跑 Stryker，所以要到整合時才會發現 |
| 規劃者的 shell 沒設 `JAVA_HOME`，單獨跑 `./gradlew :core:pitest` 失敗；`verify.sh` 本身會自動設定 | M2 整合 | 單獨跑 Gradle 前先設 `JAVA_HOME="/c/Program Files/Android/Android Studio/jbr"` |

## 7. 下次照做時的檢查清單

- [ ] 規格範例表已逐列確認、已凍結，凍結前用草稿實作確認測試能被滿足
- [ ] 接口、檔案所有權、各線的 `--lane` 驗收範圍都寫進計畫書
- [ ] 起跑前在 master 跑過每一條線的檢查，失敗的只有該線未實作的規格列
- [ ] `verify.sh` 新增的檢查，用「會觸發它的輸入」實際跑過一次
- [ ] worktree 準備腳本跑完，確認建置需要的本機檔都在
- [ ] 整合順序事先寫好；整合後只跑一次 `--full`
- [ ] 修訂架構約束時，搜尋舊里程碑的凍結規格測試有沒有檢查同一件事，要一起修訂（M2 漏掉 M0 的 S15）
- [ ] 突變測試的測試指令不要用萬用字元，一個一個列出來，並確認每支測試只讀 `backend/` 裡的檔案
- [ ] 計畫書的階段切法要對齊凍結規格測試 import 的函式，否則就直接寫明「這幾個階段一起驗收」
- [ ] 接口裡的畫面狀態（例如泡泡由誰打開）要寫明由哪一條線負責
