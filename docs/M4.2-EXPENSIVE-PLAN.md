## 0. 執行協定（最高優先，違反即為失敗）

### 0.1 不提問
全程不得向使用者提問，包含確認、選擇、澄清。
未明訂處依 §7 預設值表處理；§7 未涵蓋時選擇最保守的做法，並將決策與理由記錄在 DECISIONS.md。
不得因為缺少憑證、外部服務、或手機實測而停下來詢問。

### 0.2 工作循環
    階段實作 → 執行 ./verify.sh → 全綠？
                                  ├─ 是 → 下一階段
                                  └─ 否 → 自動修正 → 重跑

### 0.3 錯誤指紋斷路器【條款 1】
每次修正前，取失敗訊息的前三行做正規化後雜湊，得到一枚「錯誤指紋」，記錄下來。
若同一枚指紋第二次出現，**立刻停止該項目**，寫入 BLOCKERS.md
（含指紋、完整錯誤、已嘗試的修法、你判斷的根因），然後繼續處理其他項目。
輪數上限作為第二道防線，設為 3。
**不得為了讓指紋不同而改寫錯誤訊息或包裝例外。**

### 0.4 分層驗收【條款 2】
verify.sh 分三層，依序執行，前一層失敗就不進入後一層：

- **L1（秒級）**：靜態檢查、匯入檢查、grep 類的結構與架構檢查
- **L2（十秒級）**：單元測試與編譯（`:core:test`、`:app:compileDebugKotlin`、`node --test`），不含覆蓋率統計
- **L3（分鐘級）**：`assembleDebug`、Lint、突變測試、報告、完整回歸

**各階段的驗收只跑 L1 與 L2（`./verify.sh`）。L3（`./verify.sh --full`）只在最後一個階段跑一次。**
不得在 verify.sh 中吞掉任何一層的失敗回傳碼。

### 0.5 成本記錄【條款 6】
每階段結束時在 PROGRESS.md 記錄：該階段的修正輪數、出現過的錯誤指紋清單、每個驗收項各失敗過幾次。
全案結束時匯總成一張表，放在最終報告開頭。

### 0.6 版本控制
直接在目前分支工作（先確認不是有未提交變動的狀態；有則先 commit 保存）。
每階段完成且驗收通過後 commit 一次，訊息用繁體中文，以「M4.2：」開頭，結尾加 `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>`。
不設遠端、不 push、不 checkout 其他分支、不 merge、不 rebase。
不得加入 `.idea/`、`tools/push.json`、`frames/local/`、`backend/assets/character/frames/`、`backend/node_modules/`、`package-lock.json`。

### 0.7 語言與程式風格
所有註解、文件、commit 訊息、使用者看得到的文字使用**繁體中文（臺灣用語）**。
- **JavaScript（`backend/core/`、`backend/web/`）**：照現有 `core/emotion.js`、`web/renderer.js`、`web/ma-render.js` 的寫法：ES module、`// 常數定義`、`// 功能函數定義`、箭頭函式、`const`、不加分號、每個函式上方一行中文註解、常數集中在檔案上方。
  範例（照這個樣子）：

- **Kotlin**：每個函式上方一行中文註解；關鍵行尾加簡短中文註解；常數集中在檔案上方並加 `// 常數定義`。先讀 `core/.../chat/Chat.kt`、`app/.../ChatActivity.kt`、`core/.../ma/MaModels.kt`，照它們的寫法。
- **程式碼檔一律用 Write／Edit 工具寫，不用 shell heredoc**（含反斜線的內容會被吃掉）。
